# SleepVivo のデータ構造

SleepVivo の記録には、HMD などで観測したデータ、アプリの制御や判断の記録、本人の回答があります。たとえば、静止区間と起床予定時刻を重ねて見る場合は、観測のイベントとアプリ側の記録を照合します。

## 観測データの4つの層

| 層 | 保存される記録の例 | 分析で使う場面 |
| --- | --- | --- |
| L0 生観測 | HMD の位置、向き、速度、装着・接続・トラッキングの状態、記録の間隔 | 波形で動きの形や時刻を確認し、信号の欠落と実際の静止を切り分ける |
| L1 時間窓の特徴量 | 一定の時間窓でまとめた動き、静止、姿勢、観測品質 | 短い変化や長めの傾向を比べ、イベントの前後を調べる |
| L2 イベント | 静止区間、まとまった動き、覚醒候補などの点や区間 | 波形に重ねて候補の位置や継続時間を確認する |
| L3 保存済み要約 | 観測範囲ごとの集計、評価可能時間、品質、欠測 | 同じ定義と集計範囲を持つ記録を比較する |

保存される層や項目は、SleepVivo の版、記録設定、利用できた観測源によって異なります。L0 の詳細波形は主に開発・診断用の記録に含まれるため、L1〜L3 があっても L0 が保存されていない場合があります。保存されていない波形を特徴量や要約から復元することはできません。

!!! note "観測・制御・本人の評価を区別する"
    静止は HMD の動きが少なかった観測です。覚醒候補は記録上の候補です。アプリの入眠・起床支援の状態は制御の経過を示します。生理的な睡眠段階や睡眠の良否を判断するには、研究目的に適した別の測定や本人の報告と照合してください。

## 観測以外の記録

| 確認したいこと | 参照する記録 |
| --- | --- |
| 明るさや音量の変更が実際に行われたか | raw ログの制御・実行記録 |
| どの操作や予定に応じて処理が進んだか | semantic ログの操作・判断・状態遷移の記録 |
| 本人がどう感じたか | [睡眠ログ](../user-guide/sleep-logs.md)に対応する任意の起床後アンケート |
| 音や操作の候補を調べたい | 保存されている場合は、音や操作の観測・要約。発話様・いびき様の候補は音の分析結果 |

CSV Exporter の主入力は完了した観測セッションです。対応する raw・semantic・research のセッション JSON は、同じ観測セッションへの関連ログとして追加できます。睡眠ログ画面の履歴、アンケート、音や操作の専用記録、研究送信データは、取得や照合ができるかをそれぞれ確認してください。Exporter の対応入力は[入力元を選ぶ](csv-exporter.md#exporter-input)に記載しています。

Research Program で扱うデータは同意と送信条件を満たす要約です。通常の研究送信には、詳細な HMD トラッキングや原音声・文字起こしは含まれません。研究参加を停止すると新規送信が止まり、過去の送信済み記録については個別に相談できます。[研究に使う情報](../research-program/collected-data.md)と[プライバシー](../research-program/privacy.md)をご覧ください。

## 端末に保存されるファイル

Windows では、既定のアプリデータフォルダー `%APPDATA%\com.fleabane.sleepvivo` を開くと、保存されている記録の種類を確認できます。フォルダー構成の例です。

```text
com.fleabane.sleepvivo/
  observation-traces/
    YYYY-MM-DD/
      <観測セッションID>/
        manifest.json
        chunks/
        feature-windows/
        pose-features/
        motion-features/
        clock-ledger/
        events/
        session-summary/
  raw-logs/
    YYYY-MM-DD/<セッションID>.json
  semantic-logs/
    YYYY-MM-DD/<セッションID>.json
```

観測セッションの `manifest.json` は記録の版、開始・終了、チャンクなどを特定する入口です。チャンクには、JSON レコードが1行ずつ入った NDJSON や、その gzip 圧縮版があります。コピーするときはセッションフォルダー一式を保持します。フォルダー一覧は保存場所の例です。すべての項目が必ずそろうわけではありません。

## セッションと時間をそろえる

- **分析単位を決める。** 観測セッションは記録の単位です。睡眠ログの区間や要約の集計範囲が、観測セッション全体と一致するとは限りません。バンドルのセッション ID と、要約の `scope_id`・`scope_kind` を確認します。セッション全体とその内側の区間の要約を足すと、同じ観測を二重に数えることがあります。複数の記録を結びつけるときは同じ ID や記録済みの対応情報を使います。
- **共通の時刻に合わせる。** CSV の `elapsed_s` は `bundle.json` の `origin_utc` からの経過秒です。表ごとに最初の値が異なる場合があります。各表を個別に 0 秒から始め直すと、イベントとの位置関係がずれます。たとえば UTC 原点が 12:00:00、行の `elapsed_s` が 90 なら、その行は 12:01:30 UTC です。
- **粒度と切れ目を確認する。** L0 と特徴量は元の記録間隔を保ち、別表になります。位置の m、速度の m/s などの単位はチャンネルごとに確認します。単位の記録がない値には独自に単位を付けないでください。時間窓の幅と、次の窓までの間隔は別の値です。時刻の飛びや記録元の切替では、連続区間が分割されたり、表内の切れ目が記録されたりします。
- **外部計測の照合条件を記録する。** ウェアラブルやアンケートと合わせる場合は、タイムゾーン、時計のずれ、観測した期間、装着や測定の有無を確認します。VR 外や HMD を外していた時間の状態は、HMD の記録だけでは判断できません。

## 品質と再現性を確認する

1. 研究の問いに合わせ、対象者・期間・観測セッション、使う層、比較単位を決めます。
2. 実際に観測できた時間と、接続不良・欠測・品質不足で評価できない期間を確認します。予定された範囲、実際に観測できた範囲、品質条件を満たした範囲を分けて扱います。件数を比べる場合は、評価可能時間などの分母を記録します。
3. `bundle.json` の単位・元フィールド・版と、行来歴 CSV の元ファイル・元レコード番号を確認します。補完した値は `transformations.csv` で位置と理由を追跡します。ゼロに置換した値を観測上のゼロとして数えないようにします。
4. 元ログ、出力バンドル、使用したツールの版、出力対象、補完・除外条件、集計方法を対応づけて保管します。要約を比べるときは、集計範囲と指標定義をそろえます。

CSV やバンドルには時刻、識別子、元のイベント内容が含まれる場合があります。保管・共有には研究の同意範囲と取り扱いルールを適用し、共有用のデータは必要な項目に絞ります。
